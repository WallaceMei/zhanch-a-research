## 1. 典型错误案例

### 1.1 协鑫能科 002015.XSHE

日志出现：

```text
TRADE_ACCOUNTING_WARN|stock=002015.XSHE|name=协鑫能科|reasons=sell_amount_exceeds_buy
buy_amount_accum=2900
sell_amount_accum=2250
final_sell_amount=700
```

问题：

```text
2250 + 700 = 2950
buy_amount_accum = 2900
多记 50 股
```

### 1.2 万邦德 002082.XSHE

日志出现：

```text
TRADE_ACCOUNTING_WARN|stock=002082.XSHE|name=万邦德|reasons=sell_amount_exceeds_buy
buy_amount_accum=1300
sell_amount_accum=650
final_sell_amount=700
```

问题：

```text
650 + 700 = 1350
buy_amount_accum = 1300
多记 50 股
```

## 2. 根因判断

A 股交易数量存在 100 股整数约束。

例如：

```text
理论请求卖出 650 股
聚宽实际调整为 600 股

理论请求卖出 150 股
聚宽实际调整为 100 股
```

当前 v1.1.2 账本可能在 `submit_partial_stage_change` 中，订单返回非 None 后，直接按理论请求数量入账。

这会导致：

```text
sell_amount_accum 记录理论数量
最终清仓 final_sell_amount 记录真实剩余数量
二者相加超过 buy_amount_accum
```

## 5. 修复原则

### 5.1 partial sell 不能直接按理论 amount 入账

禁止逻辑：

```python
sell_amount_accum += requested_amount
```

如果 `requested_amount=650`，但聚宽实际成交 600，则账本只能记录 600。

### 5.2 优先使用实际成交数量

partial sell 入账数量优先级：

```text
1. order 对象中可可靠读取的实际成交数量 / 调整后数量
2. 持仓同步中观察到的真实持仓减少数量
3. 不可靠时只登记 pending，不累计 sell_amount_accum
```

### 5.3 持仓变化是最终可信来源

在 `sync_position_meta_with_real_positions` 中，基于真实持仓变化确认 partial sell：

```text
actual_sold_total = previous_amount_before_partial - current_amount
newly_filled = actual_sold_total - pending_partial_filled_amount
```

然后限制：

```text
remaining_to_account = buy_amount_accum - sell_amount_accum
newly_filled = min(newly_filled, remaining_to_account)
```

只有：

```text
newly_filled > 0
```

时才累计：

```text
sell_amount_accum += newly_filled
sell_value_accum += actual_or_estimated_price * newly_filled
realized_pnl_accum += pnl_value
```

## 6. 订单实际数量读取建议

可以新增辅助函数，例如：

```python
def _extract_actual_close_amount_from_order(order_obj, requested_amount, amount_before):
    ...
```

建议读取顺序：

```text
1. order_obj.filled
2. order_obj.filled_amount
3. order_obj.amount
4. order_obj.deal_amount
5. order_obj.traded_amount
6. 从 order_obj.error 或 str(order_obj) 中解析 “调整为 600” 这类文本
```

但必须校验：

```text
actual_amount > 0
actual_amount <= amount_before
actual_amount <= requested_amount 或者属于聚宽调整后的合理数量
```

如果无法可靠读取，则返回 None，不要强行入账。

## 7. 100 股整数调整处理

如果无法从 order 对象读取实际成交数量，但日志或聚宽规则显示请求数量会被 100 股整数约束，可以在 pending 中记录：

```text
requested_amount
lot_adjusted_amount
amount_before
expected_after_amount
```

但注意：

```text
lot_adjusted_amount 只能作为辅助判断，不应替代真实持仓变化。
```

最终账本累计仍应以：

```text
真实持仓减少数量
```

为准。

---

## 8. pending 状态修复

当前可能存在的问题：

```text
pending 完成判断使用 requested_amount。
```

例如：

```text
requested_amount = 650
actual_filled = 600
```

如果判断：

```text
actual_filled >= requested_amount
```

就会误判为未完成。

修复要求：

```text
pending 完成判断应使用 actual_order_amount / lot_adjusted_amount / observed_filled_amount。
```

不能让 650 请求、600 实际成交的订单一直处于 pending。

---

## 9. finalize_exited_position 校验

最终清仓时：

```text
accounted_sell_amount = sell_amount_accum + final_sell_amount
```

正常情况下：

```text
accounted_sell_amount == buy_amount_accum
```

至少不能出现：

```text
accounted_sell_amount > buy_amount_accum
```

对典型案例，修复后应满足：

```text
协鑫能科：
buy_amount_accum=2900
sell_amount_accum + final_sell_amount = 2900

万邦德：
buy_amount_accum=1300
sell_amount_accum + final_sell_amount = 1300
```

禁止简单粗暴做：

```python
sell_amount_accum = min(sell_amount_accum, buy_amount_accum - final_sell_amount)
```

这种静默截断只能掩盖错误，不能作为主要修复方式。

如果异常仍然存在，应继续输出：

```text
TRADE_ACCOUNTING_WARN
DRAGON_LOSS_CLASSIFY_SKIP
```
