## 1. v1.2.0 版本目标

新版本号：

```text
v1.2.0-auction-prefilter
```

核心目标：

```text
减少 09:28 Dragon 全市场竞价选股中的 get_call_auction 调用数量。
```

已知主要瓶颈链路：

```text
post_auction_prepare
→ update_dragon_mode
→ get_dragon_stock_list_A
→ _get_dragon_stock_list_A_impl
→ get_call_auction
```

profile 诊断结果显示：

```text
update_dragon_mode 约 1810s
get_dragon_stock_list_A 约 1810s
_get_dragon_stock_list_A_impl 约 1778s
get_call_auction 调用约 40169 次
get_call_auction 主调用行耗时约 802s
```

因此真正有效的提速方向是：

```text
在调用 get_call_auction 前，先用不依赖竞价数据的日线稳定因子做预筛。
```

## 2. 重要性质：这是策略优化，不是等价优化

v1.2.0 和 v1.1.3 不同。

v1.1.3 是 bug fix，目标是不改变交易逻辑。

v1.2.0 是性能优化，会主动减少进入 get_call_auction 的股票数量，因此可能改变候选池、买入标的、收益曲线。

必须明确标记：

```text
Change Type:
- auction-prefilter-v1
- strategy-performance-experiment
```

不能把 v1.2.0 当作纯 bug fix。

## 5. 预筛设计原则

### 5.1 预筛只能使用 get_call_auction 之前已经可获得的数据

允许使用：

```text
日线 close/high/low/volume/money
前一交易日收盘价
近 N 日涨跌幅
近 N 日成交额
近 N 日振幅
是否停牌
是否 ST
上市时间
流通市值/市值，如果当前代码已有
当前代码原本已经批量获取的数据
```

禁止使用：

```text
get_call_auction 结果
auction current
auction volume
auction amount
auction open_ratio
任何需要逐票 get_call_auction 后才能知道的数据
```

### 5.2 先做宽松预筛，不要一步砍太狠

目标：

```text
把进入 get_call_auction 的股票数从 500+ 降到 150~250。
```

不要直接降到：

```text
50
80
100 以下
```

第一版建议：

```text
max_auction_prefilter_count = 250
```

如果原始候选不足 250，则不强行裁剪。

### 5.3 预筛分数只负责排序，不替代 Dragon score

新增预筛分数只能用于：

```text
决定哪些股票进入 get_call_auction
```

不能替代：

```text
原 Dragon score
原 tpl 判断
原 deep_water 条件
原最终排序规则
```

进入 get_call_auction 后，原有 Dragon 评分和筛选逻辑继续执行。

## 6. 建议的预筛因子

建议使用轻量、稳定、不会过度拟合的日线因子：

```text
1. 近 5 日成交额均值
2. 近 10 日成交额均值
3. 昨日成交额
4. 近 5 日涨幅
5. 近 10 日涨幅
6. 距离近 20 日高点的位置
7. 近 10 日振幅
8. 昨日是否强势收盘
```

示例方向：

```text
daily_prefilter_score =
    成交额分位
  + 近期强度分位
  + 接近高位分位
  + 振幅活跃度分位
```

注意：

```text
不要引入未来函数。
不要使用当天收盘数据。
不要使用 09:28 后才知道的数据。
```
