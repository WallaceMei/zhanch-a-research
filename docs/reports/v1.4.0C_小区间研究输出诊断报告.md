### 技术根源剖析：
漏斗瓶颈存在于 **从预筛选（Prefilter）到核心候选人（Core Candidate）的生成代码中**，具体由以下两个技术 Bug 造成：

*   **API 循环调用导致被限流跳过（主因）**：
    在 `generate_core_candidates` 函数中，代码遍历通过 prefilter 的所有股票（日均高达 1,732 支），对每支股票都单独执行一次 `get_price` 查询当日开盘行情：
    ```python
    day_df = get_price(stock, start_date=str(date), end_date=str(date), frequency='daily', ...)
    ```
    这导致在一个交易日内产生 **1700+ 次 API 独立网络请求**，整月测试产生 34,000+ 次请求，这在聚宽研究环境中必然会触发限流或连接超时。由于代码使用 `except Exception: continue` 进行静默处理，所有失败的查询被直接跳过，导致最终有效候选股数量恒为 0。
*   **集合竞价量比 `auc_ratio` 模拟计算错误导致评分严重偏低（次因）**：
    在模拟脚本中，`auc_ratio` 计算方式为：
    `auc_ratio = day_price['volume'] / max(float(df['volume'].iloc[-1]), 1)`，其中 `day_price['volume']` 取的是**当日整天交易量**。而真实策略使用的是 9:25 的**集合竞价成交量**。整日交易量通常是集合竞价量的数十到上百倍，导致算出的量比数值（约 0.5 到 2.0）被严重放大。
    这使得在 V3 评分逻辑中：
    `score += max(0, 0.03 - auc_ratio) * 8.0` 项直接归零（本应有加分）。该错误计算将所有股票的得分拉低了约 `0.20`，导致即使有股票成功获取了价格，也会因为达不到 `DRAGON_MIN_SCORE = 0.70` 的阈值而被完全过滤。
*   **趋势过滤历史长度不足（Minor）**：
    获取 20 日历史日线的 `count=20` 导致 `len(closes)` 最高为 20。而个股趋势过滤判断条件为 `if len(closes) >= 21:`，导致此过滤段实际上被恒判定为 False 而跳过。

本次诊断工作完全局限在**交易执行与取数链路的 Bug 定位**上，目的是让模拟引擎能够正确对齐原策略的打分和过滤行为。**不涉及任何参数的放宽、阈值的下调或指标的过度优化。** 严禁为了产生交易而建议降低打分门槛或放宽过滤范围。同时，一个月的测试仅用于诊断链路，不应据此对策略长期有效性做任何定性判断。

## 8. 下一步建议

为使模拟链路正常工作，建议优先进行以下三项 Bug 修复：

1.  **批量行情查询重隔**：
    修改 `generate_core_candidates` 中的取数逻辑。严禁在循环内对单支股票调用 `get_price`。应在循环外对所有通过 Prefilter 的股票列表（`prefiltered_stocks`）进行**单次批量 `get_price` 调用**，在内存中完成开盘数据的匹配，以彻底解决限流和连接超时问题。
2.  **量比计算修正**：
    在模拟脚本中调用 `get_call_auction` 接口获取 9:25 的真实集合竞价成交量；若无法获取，应根据历史平均比例进行折算折中，以修正 `auc_ratio` 估算并恢复 V3 得分项中应得的 `0.10~0.20` 加分，使评分对齐真实策略。
3.  **对齐历史数据长度**：
    将获取历史行情的 `count` 从 20 提高到 25 或 30，确保个股趋势过滤的 `len(closes) >= 21` 能够被触发执行，使过滤器工作机制与真实策略一致。
